sqwen targets exactly one architecture family, qwen35moe: Gated DeltaNet linear attention + full attention + MoE. The whole model (Q4_K_M, 20.2 GiB) resides on a single 24 GB GPU and is exposed as an OpenAI-compatible HTTP API.

It is not a drop-in replacement for llama.cpp. It squeezes every drop out of 24 GB of VRAM.

Once free VRAM drops below ~500 MiB, launching any other GPU program triggers WDDM paging and throughput falls off a cliff. This is the verbatim warning from the README: -c 200000 fits, but leaves only ~380 MiB.

Note: the runtime overhead (~2.0 GiB) and driver reservation (~370 MiB) segments are approximations back-derived from two anchors in the README (172K → ~530 MiB left; 200K → ~380 MiB left); weights and KV are the documented values (KV = tokens × 5.6 KiB).

01 · Context cost

Why context costs almost nothing

The KV cache is quantized to q4_0 — both K and V — covering only the 10 full-attention layers: 5.6 KiB per token. The state of the GDN linear-attention layers is fixed-size and does not grow with sequence length. So pulling -c from 172K to 200K slows things down by just 0.4%.

In one line: context eats VRAM, not compute.

02 · Measurements

Speculative decoding: deeper is a net loss

The MTP head has built-in drafting capability. Intuition says longer drafts win; the measurements say the opposite: the marginal cost of one draft token is ≈ 60% of a full decode (verification must re-read the expert weights it activates), while acceptance rate decays with position (pos0 ≈ 0.9, pos1 ≈ 0.7). Same machine, greedy, ABBA interleaving:

The optimum is one draft per step. The engine measures both "0 / 1" modes online and locks in the winner (--spec-adaptive, on by default) instead of tuning parameters by guesswork: each candidate gets 5 rounds of samples, probing starts only after the first 32 steps (~45 tokens), compared by median throughput.

Tool calling: tool definitions are rendered into the chat template, and tool_calls are extracted from the text after generation — the same route as llama.cpp. In streaming mode, tool calls are emitted in one block in the final chunk, with multi-turn role: "tool" results supported.

Prompt cache: prefix reuse + GDN state checkpoints. First-token latency on multi-turn conversations is about 11× better.

sqwen.exe server "E:\models\BigBang-v1.i1-Q4_K_M.gguf" \
  --port 8100 -c 172032 -b 2048 -u 512 -t 8 \
  --template "E:\models\chat_template_v22.5.jinja" \
  --spec-type draft-mtp \
  --temp 0.1 --top-k 40 --top-p 0.95 --min-p 0.05 \
  --repeat-penalty 1.08 --repeat-last-n 128 \
  --reasoning on --reasoning-effort medium --reasoning-budget 2048 \
  --reasoning-format deepseek --queue-capacity 8
# --repeat-penalty 1.08 --repeat-last-n 128 — do not skip these: the default 1.0 turns it off,
# and at low temperature the model cannot stop repeating once it starts (in agent scenarios this looks like "hanging")

04 · Trade-offs

All deliberate trade-offs

  • SerialRequests are fully serial (single engine); beyond --queue-capacity you get a 429.
  • ParametersNo support for stop, n>1, logprobs, response_format, or JSON Schema constrained decoding.
  • tool_choice"required" and named functions are not enforced; only "none" is honored.
  • Tool JSONOccasionally contains unescaped quotes: the server fixes common shapes, and falls back to plain text rather than emitting a broken call when it can't.
  • PlatformWindows build (MSVC + CUDA 12.5); other platforms unverified.
  • ScopeSupports only the qwen35moe architecture family; an early-stage project, not a drop-in replacement for llama.cpp.
